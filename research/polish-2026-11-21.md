# Local polish pass — runtimes, a trained model and the edit verifier, 2026-11-21

Question: can a local model give Voiceour Typeless-style cleanup — fillers, self-corrections, small grammar
fixes, spoken lists — fast and safely enough on this Mac, and which runtime should run it? Nothing here changes
the app: [README › What happens to the words](../README.md#what-happens-to-the-words) still holds, and every
artifact below is bench-only or published separately.

Setup: one Apple M4 Pro (10 performance + 4 efficiency cores), 24 GB, macOS 27.3, AC power, powermode 2, no
thermal warning recorded; training on `ubuntu-devbox` ([devbox/README.md](devbox/README.md)). The working lab
lived outside the repository (`~/polish-lab`: downloads, per-runtime harnesses, raw results, private History
runs). The repository keeps what later work needs: the edit verifier and the held-out cases
([`bench/polish/`](../bench/polish/)), the in-process runner (`voiceour-bench polish`, `Vendor/qwen3/`), the
curated numbers ([`benchmarks/results/20261121-polish-runtime-screen.json`](../benchmarks/results/20261121-polish-runtime-screen.json))
and the training environment pin ([`devbox/envs/polish-train/`](devbox/envs/polish-train/)).

## Verdicts

| question | answer |
| --- | --- |
| Fastest runtime | ggml (llama.cpp b12606) with n-gram drafts on the GPU and MLX with prompt lookup tie: p50 45 vs 43 ms, 155-word case 340 vs 311 ms. ggml needs 0.3 GB of process memory against MLX's 1.7 GB and no new dependency, so ggml it is. |
| Neural Engine | Core ML on the Neural Engine (Spokenly's export) is 13–16% slower than ggml (p50 52 vs 45 ms, 155 words 385 vs 340 ms); see [Energy](#energy). Core AI is slower on the GPU and on the Neural Engine and compiles for about 4 minutes on first load. |
| In-repo runner | `Vendor/qwen3` on the vendored ggml 0.19.0 gives llama.cpp's greedy output on all 1,036 prompts and its speed without drafts (88 vs 88 ms). With drafts it trails (60 vs 45 ms; 503 vs 340 ms): ggml 0.19.0 has no `mul_mv_mma` kernels for 2–9-token batches. |
| Our model | `voiceour-polish` v1, a LoRA on Qwen3-0.6B-Base trained on 20,001 synthetic pairs, passes 35 of 36 held-out checks against Spokenly Cleanup 1's 21, at the same latency. |
| Safety | On 498 real dictations the model deleted content words in 103. A deterministic edit merge restores them and keeps the allowed edits, so any model pass would have to run behind it. |

## Runtime screen

The same weights everywhere: `spokenly/cleanup-1` (Apache-2.0, a Qwen3-0.6B-Base fine-tune) at `cd95b502`, which
Spokenly publishes as safetensors, a Q8_0 GGUF and a Core ML Neural Engine export. Prompt `"text: " + input +
"\nout:"`, greedy, stop at `<|endoftext|>`. One process per config: load, two warm-ups, then 3 repetitions over
the 36 held-out cases in [`bench/polish/cases/agent36.jsonl`](../bench/polish/cases/agent36.jsonl), each request
timed from input string to output string. Every model run held one exclusive lock, and the whole set ran
forward and then in reverse; each cell is the median over both passes. G01 and G02 are the 97- and 155-word cases.

- **Drafting is the lever.** Cleanup output is mostly a copy of the input, so drafting from the prompt halves
  p50 and cuts long dictations by about 3× on every runtime that has it, with byte-identical output in all 36
  cases (and 999 of 1,000 test prompts for `voiceour-bench polish`: one near tie, logit gap 0.0014).
- **Process MB is not one measure.** llama.cpp, MLX and Core ML report `/usr/bin/time -l` peak footprint;
  `voiceour-bench polish` reports `task_info` and reads 821 MB under `/usr/bin/time`, whose count includes the
  604 MiB of mapped weights the vendored Metal backend keeps resident. Core ML's figure leaves out the Neural
  Engine's own copy of the model.
- **Output parity.** Against bf16 MLX, the Q8_0 builds differ on 3 of 36 cases, MLX 8-bit on 1, Core ML on 1, and
  Core AI's 4-bit and mixed-bit exports on 8 and 6: the quantization, not the runtime, decides the text.
- **CPU-only.** llama.cpp Q8_0 on 10 CPU threads ran at p50 79 ms in the forward pass and 146 ms in the reverse
  pass, which overlapped a model conversion; Core ML on the CPU at 99 and 115 ms. Neither is a candidate.
- **Core AI first load.** The Neural Engine exports compile for 228–242 s the first time (cached after); the
  GPU exports specialize each new prompt shape on first sight.
- Full rows, devices and evidence per config: the results file.

## Energy

Not measured. Without root, macOS 27.3 reports zero for the CPU, Neural Engine and DRAM rails of IOReport's
"Energy Model" group; only the GPU rail moves. The battery controller's `PowerTelemetryData` accumulators were
tried next, with an idle window and a 108- against a 324-request run per config: they update too rarely for
windows of 10–20 s, and the run produced idle readings of 0 W and negative energies, so no number is reported.
The one solid reading is the GPU rail: 0.56 W while Core ML ran on the Neural Engine, against 11.8 W while the
same model ran on the GPU. A per-request energy comparison needs `sudo powermetrics --samplers
cpu_power,gpu_power,ane_power` around the same runs.

## The in-repo runner

`Vendor/qwen3` ports llama.cpp b12606's Qwen3 decoder onto the vendored ggml without changing ggml: mapped
read-only weights, an F16 KV cache of 2,048 cells, flash attention, greedy decoding with ngram-simple drafting
verified in one graph evaluation. The Swift tokenizer in `voiceour-bench` equals Hugging Face `tokenizers` on a
committed 23-text fixture, on all 36 held-out prompts and on all 1,000 test prompts. Greedy output equals
llama.cpp's on all of them. The drafting gap is the kernel: b12606's ggml 1.0 runs 2–9-token batches through
`kernels/mul_mv_mma.metal`, which ggml 0.19.0 does not have; drafting itself matches llama.cpp step for step
(221 evaluations, 1,116 drafted tokens, 678 accepted on agent36). Closing it needs a `Vendor/ggml` refresh or a
`VOICEOUR PATCH` backport, and Granite's parity would have to be re-proven.

## Training data

22,001 synthetic pairs — 20,001 train, 1,000 valid, 1,000 test, stratified — at $5.90 through OpenRouter, from
open-weight teachers only: `openai/gpt-oss-120b` (Apache-2.0) and `deepseek-ai/DeepSeek-V4-Flash` (MIT). No
user dictation went into them. 35% are already clean (target equals input), traps included ("look like", "Do you
know why", injected instructions); 60% are prompts dictated to coding agents. Filler presence matches the
owner's 500 dictations: "you know" 29.5% (30%), "like" 38.7% (40%), "basically" 11.2% (11%), "kind of" 14.2%
(16%). Every needs-change pair passes `verify(input, target)`. Weak spots: some inserted fillers sit in
unnatural places, and teacher texts run shorter than real long dictations (p90 78 words against 100).

## Model v1

LoRA rank 32, alpha 64, dropout 0.05 on all seven projections of Qwen/Qwen3-0.6B-Base at `da87bfb6`; prompt
`"text: " + input + "\nout:"`, completion `" " + target + "<|endoftext|>"`, loss on the completion only; two
epochs, 1,251 steps of 32 sequences, learning rate 2e-4 cosine, fp16 autocast on the RTX 2070 SUPER; 26
minutes, valid loss 0.282 → 0.0031. The trainer checksummed every host↔GPU copy and every saved tensor, and
greedy outputs on five held-out cases were identical on CUDA fp16, CUDA fp32 and CPU fp32.

## The edit verifier

[`bench/polish/polishlab.py`](../bench/polish/polishlab.py) `verify(src, out)` accepts a change only when it is a
filler deletion (um, uh, like, you know, kind of, sort of, basically, sentence-opening so/okay/right/well, just),
a stutter or repeated phrase of up to four words, a self-correction deletion that removes the cue together with
the words it retracts, a one-word inflection (was→were, checks→check, doesn't→don't; negations never), a spoken
list marker turned into a numeral, or punctuation and case outside protected tokens (digits, paths, flags,
internal capitals, Glossary terms). `merge_allowed(src, out)` applies that rule per edit: it keeps each allowed
change and restores the source everywhere else. Two rules came from failures found here: "I mean" is not a
filler, and a cue word ("scratch that", "no", "I mean", "actually") may not be deleted without the words before
it, because deleting it alone turns a retraction into an instruction.

  words" ([.omp/RULES.md](../.omp/RULES.md)) unless the contract is rewritten around the edit merge.

  restarts, discourse phrases that carry meaning); the owner can judge the 324 changed dictations in the private
